# GitHub math rendering rules

These rules describe what the bundled linter checks and why. They come from
GitHub's GFM + MathJax pipeline: Markdown is parsed first, then math is
extracted and rendered. Some LaTeX is rejected outright; other constructs are
mangled before MathJax ever sees them.

Use fenced examples below as illustrations. The linter ignores fenced code
blocks and inline code, so examples can show broken math safely.

## 1. Display math placement

A `$$` delimiter must be alone on its line, at column 0, with blank lines
before and after.

Indented display math (for example inside a list item) is rendered as literal
text instead of math. A `$$` delimiter sharing a line with prose is not
recognized as a display block.

Bad:

```markdown
Text before.
$$
x = 1
$$
Text after.
```

Bad:

```markdown
- An item

  $$
  x = 1
  $$
```

Good:

```markdown
Text before.

$$
x = 1
$$

Text after.
```

If the math belongs to a list item, move the display block out of the list
rather than indenting it. Inline math can stay inside the list text.

## 2. `\text{x}_{sub}` and double escaping

GitHub HTML-escapes the math source before MathJax processes it. With
`\text{...}_{...}` on one line, the escaping can happen twice: MathJax
receives `&amp;` instead of `&` and fails with `Misplaced &`.

The linter flags `\text{...}_` and `\mathrm{...}_`. Add one space between the
closing brace and the underscore; the space is ignored by MathJax.

Bad:

```markdown
$\text{Var}_{i} + \text{Var}_{j}$
```

Good:

```markdown
$\text{Var} _{i} + \text{Var} _{j}$
```

## 3. Inline math must stay on one line

Inline `$...$` math must:

- fit on a single line,
- have no whitespace just inside the delimiters,
- contain no `\\` (GitHub rejects the whole expression).

Bad:

```markdown
The value is $ x $ when $a \\ b$.
```

Good:

```markdown
The value is $x$.

$$
a \\
b
$$
```

Every `$` in the file must belong to a pair. The linter counts `\$` as a
delimiter too, so use `&#36;` for a literal dollar amount (or a code span,
which the linter skips).

## 4. Blocked macros and stripped spacing

GitHub blocks `\operatorname` and `\phantom` outright. It strips `\!` and
renders `\,` as a comma. Remove `\,`, `\:`, `\;`, and `\!`.

For a named operator, build it with `\mathop{\mathrm{...}}`. `\phantom` has no
direct replacement; remove it and restructure the expression or use spacing
that GitHub supports.

Bad:

```markdown
$\operatorname{argmax}_x f(x)$
```

Good:

```markdown
$\mathop{\mathrm{argmax}}_x f(x)$
```

Bad:

```markdown
$a\,b \: c \; d \! e$
```

Good:

```markdown
$a b c d e$
```

## 5. Unsupported environments

GitHub does not support the `align`, `align*`, `equation`, `equation*`,
`gather`, or `gather*` environments.

- `align` → use `\begin{aligned}...\end{aligned}` inside `$$...$$`.
- `equation` → delete the environment and keep the expression in `$$...$$`.
- `gather` → split into separate display blocks.

Bad:

```markdown
$$
\begin{align}
a &= b \\
c &= d
\end{align}
$$
```

Good:

```markdown
$$
\begin{aligned}
a &= b \\
c &= d
\end{aligned}
$$
```

## 6. Bare pipes in inline math

A bare `|` can be parsed as a table column separator and break rendering. Use
`\vert` for absolute value and `\mid` for set-builder bars. The linter accepts
`\left|`, `\right|`, `\vert`, `\Vert`, `\mid`, `\lvert`, `\rvert`, and `\|`.

Bad:

```markdown
$|x|$ and $\{x | x > 0\}$
```

Good:

```markdown
$\vert x \vert$ and $\{x \mid x > 0\}$
```

## 7. GitHub Pages notes

Math on github.com renders natively. A GitHub Pages site generated by Jekyll
does not enable math by default: add MathJax or KaTeX to the site layout or
use a theme that includes it.

The linter checks the Markdown source, not the site's renderer configuration.
It cannot tell you whether MathJax was loaded on the deployed page. Keep
display math at column 0, alone, and surrounded by blank lines; that form is
accepted by GitHub's renderer and by common MathJax setups.

## 8. What the linter does not check

The linter is regex-based and intentionally narrow:

- It skips fenced code blocks and inline code.
- It does not validate TeX syntax generally, balance braces, or resolve
  macros.
- It does not detect LaTeX commands that GitHub happens to reject beyond the
  rules above.
- It cannot verify the final rendered output.

When a finding's cause is unclear, fix the reported construct first, re-run,
and preview the file on GitHub. GitHub can change its rendering pipeline; if
behavior and these rules disagree, trust the preview and update the rules.
